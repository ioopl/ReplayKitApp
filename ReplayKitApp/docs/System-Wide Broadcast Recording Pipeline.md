# System-Wide Broadcast Recording Pipeline

This document describes how the ReplayKit system-wide broadcast recording flows from the iPhone screen to the Session Artifacts player.

## End-to-end pipeline

```text
ReplayKit video buffer
    → 420f YUV
    → 32BGRA conversion
    → pixel-buffer adaptor
    → App Group/BroadcastOutput/broadcast.mp4
    → host app
    → Session Artifacts player
```

## 1. ReplayKit video buffer

When the user starts a system-wide broadcast, iOS launches the Broadcast Upload Extension. `SampleHandler` receives screen frames through:

```swift
processSampleBuffer(_:with:)
```

Video buffers arrive with `RPSampleBufferType.video`. Audio buffers may also arrive as `.audioApp` or `.audioMic`; the current local recording pipeline ignores audio.

The extension runs in a separate process from the main app, so it cannot directly update the app UI or write into the app's private container.

## 2. 420f YUV

On the physical iPhone used during testing, ReplayKit supplied video buffers with:

```text
Resolution: 886 × 1918
Pixel format: 420f
```

`420f` is a full-range bi-planar YUV video format. It is efficient for capture, but passing it directly into the H.264 writer was unreliable in this implementation.

## 3. 32BGRA conversion

Each ReplayKit pixel buffer is converted to a predictable `32BGRA` buffer using Core Image before writing.

This makes the input format explicit and avoids depending on the H.264 writer to accept the device-specific `420f` source format.

The conversion preserves the original captured resolution.

## 4. Pixel-buffer adaptor

The converted BGRA buffer is submitted through:

```swift
AVAssetWriterInputPixelBufferAdaptor
```

The adaptor accepts `CVPixelBuffer` objects and associates each frame with its ReplayKit presentation timestamp. Successful appends increment the written-video-frame counter.

The direct `AVAssetWriterInput.append(sampleBuffer)` approach was tested but failed on the physical device. The pixel-buffer adaptor plus explicit BGRA conversion is the working path.

## 5. App Group output

The main app and Broadcast Upload Extension share:

```text
group.com.apkia.replaykitapp.shared
```

The extension creates the output directory explicitly:

```text
<App Group>/BroadcastOutput/
```

The final file is:

```text
<App Group>/BroadcastOutput/broadcast.mp4
```

The explicit directory creation was important. Writing directly to an unresolved App Group path caused `AVAssetWriterStatus(rawValue: 3)` and:

```text
NSURLErrorDomain Code=-1100
The requested URL was not found on this server.
```

In this context, the message indicated that the local output path could not be resolved or created; it was not a network streaming failure.

## 6. Host app handoff

The extension writes lifecycle state into the shared App Group:

```text
broadcastActive
broadcastFinished
broadcastSessionID
broadcastFinishedSessionID
```

The host app polls these values. A unique session ID prevents a previous broadcast's completion marker from being mistaken for the current session.

When the extension finishes writing, it sets `broadcastActive` to `false` and `broadcastFinished` to `true`. The host then waits for the file to exist and verifies that it is larger than the minimum validity threshold before using it.

## 7. Session Artifacts player

Once the file is valid, the host app assigns the App Group URL to `lastVideoURL`. `PostSessionSummaryView` creates an `AVPlayer`/`VideoPlayer` for that URL.

The player therefore uses the actual MP4 generated by the Broadcast Upload Extension rather than the generated test animation.

## Diagnostics

The extension records these values for troubleshooting:

```text
receivedSamples
videoBuffers
writtenVideoSamples
broadcastVideoFormat
broadcastWriterStatus
broadcastWriterError
broadcastWriterErrorDomain
broadcastWriterErrorCode
```

Typical interpretations:

| Diagnostic result | Meaning |
|---|---|
| `receivedSamples = 0` | The extension did not receive buffers. |
| `videoBuffers = 0` | No video buffers arrived; received buffers may be audio only. |
| `videoBuffers > 0`, `writtenVideoSamples = 0` | The writer, pixel format, conversion, or output path failed. |
| `writtenVideoSamples > 0`, `writerStatus = 2` | The MP4 writer completed successfully. |

## Simulator behavior

The Simulator cannot perform true system-wide ReplayKit screen capture or Secure Enclave operations.

Simulator behavior is therefore intentionally different:

- Secure Enclave and biometric authentication are bypassed.
- Software test keys are used.
- The Simulator UI exposes `Simulate Broadcast (Simulator)`.
- The animated video is retained as a Simulator-only fallback.
- A physical device must use the real ReplayKit video pipeline and must not silently replace a failed recording with the fallback animation.

## Important lessons

1. App Group entitlements must be present on both the main app and Broadcast Upload Extension.
2. `BroadcastSetupViewController` only completes setup; it does not record frames.
3. `SampleHandler` is responsible for receiving and writing the actual screen buffers.
4. The device pixel format must be handled explicitly.
5. The output directory must exist before creating `AVAssetWriter`.
6. The host app must wait for extension finalization before opening the MP4.
7. Session IDs prevent stale shared UserDefaults values from causing false completion.
