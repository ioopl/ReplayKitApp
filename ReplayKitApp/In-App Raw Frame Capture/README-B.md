#  InAppCaptureViewModel.swift &  InAppCaptureView.swift
 
## Captures raw CMSampleBuffer frames, converts them using GPU acceleration via CIContext, and encrypts them using CryptoKit AES-GCM.

A detailed breakdown of Feature B (In-App Raw Frame Capture), how it operates under the hood, and its practical applications.

#1. What is the practical use case for this?

Option A (In-App Screen Recording) is designed to produce a local, fully finished MP4 video file.

However, in many production scenarios, you don't want a file. Instead, you need the raw video feed in real time. 
So Option B (In-App Raw Frame Capture) is designed for these scenarios:

A) Custom Low-Latency Live Streaming: Sending the screen frames directly over a WebRTC or gRPC pipeline to a streaming platform (like Twitch, YouTube Live, or an enterprise webinar tool).

B) Remote Assistance & Screen Sharing: Real-time collaborative apps (like Zoom, MS Teams, TeamViewer) where an operator needs to see your app screen instantly.

C) Real-time Video Processing: Applying real-time filters, computer vision analytics, or watermarking on the screen feed before transmitting it.

#2. How does it work?

Instead of ReplayKit writing the screen output to a file, the OS sends a callback to your app for every frame rendered on the screen (typically 30 to 60 times per second).

1) CMSampleBuffer: This is a container object generated by iOS. It holds a pointer to a CVPixelBuffer (the raw, uncompressed image data directly from the graphics hardware).

2) GPU Processing: The code uses CIContext(options: [.useSoftwareRenderer: false]) to instruct the hardware to process the frame using the GPU instead of CPU memory.

3) JPEG Compression: The raw pixel buffer is compressed into standard JPEG bytes.

4) AES-GCM Encryption: The JPEG bytes are instantly encrypted with the 256-bit symmetric key generated by the Secure Enclave.


# 3. What are those "Frames" and where do they go?

Answer: They are individual snapshots of the Screen at that millisecond.

In this demo, the encrypted frame data is processed strictly in-memory and then discarded.

Unlike Option A, which saves a video to our Photos library, Option B simulates a live broadcast transmitter. Once we stop the capture:

- The ReplayKit pipeline is torn down.
- The memory buffer holding the last frame is released.
In a production system, instead of discarding the encryptedPayload, we would pass it to our socket or gRPC network stream:

// In a production App, the frames are streamed to the network: `self.networkService.sendFrame(encryptedPayload)`

Since there is no backend server connected yet, the demo simply outputs performance metrics (how many frames were successfully processed and the payload size of the last encrypted frame) to prove the pipeline is active and encrypting at low latency.
